Two-minute pitch

Problem. At the start of every semester, students build their timetables by hand from a long PDF. They try section combinations until nothing clashes, then try to stay focused through classes and plan study time around them. Three separate apps cover these jobs badly, and none of them knows the class timetable.

What Semester does. You import the course schedule (PDF, CSV or pasted text), check it on a review screen, and mark the courses you must take and the ones you want, in ranked order. A branch-and-bound scheduler returns the top three clash-free timetables in milliseconds. If the courses cannot fit, it names the smallest set of MUST courses that clash, and when. One tap writes the classes to the calendar. The timetable then drives two other features: focus mode blocks distracting apps and turns on Do Not Disturb during every class, and the nightly planner fills tomorrow's free gaps with tasks.

How it is different. Everything runs on the phone, with no AI, no account and no INTERNET permission, which every build checks. The core is deterministic and tested against a brute-force oracle. Parsed data is never used until a person has reviewed it.

How it was built. I used Claude Code over six sessions with a spec-driven process. Every requirement has an ID and an acceptance test, and every decision and measurement is logged. The project has 164 JVM tests and 52 instrumented tests, and it was checked on my own Galaxy M15 running Android 15.

Demo route (about 4 minutes)

  1. Timetable → Courses → Try sample courses. The review screen opens. Point out that nothing is saved before Confirm (INV-2, "never silently wrong").
  2. Mark CS201 and MA202 as Must take and the rest as Want. Choices shows the ranking.
  3. Week shows every section, overlaps included. This is the problem the scheduler solves.
  4. Results shows the top 3 clash-free options. Open Limits and preferences, add a free day or "no classes before 9" and watch the answer change. Lock a section. Open Details for the penalty and the build time in ms.
  5. Make a clash on purpose (two MUSTs at the same time) to show the conflict sentence.
  6. Use this timetable → Add to calendar. Then Focus (Session / Apps / Insights) and Planner: add a task and tap Auto-fill.

In the browser (Appetize), blocking, DND, alarms and calendar writing can't be fully granted, so describe the real-phone results from the Numbers section.

Product and scope

Why one app instead of three?

The class timetable is the fixed skeleton of every day (decision D-01). If the planner knows the classes, it can find the real free gaps. If focus mode knows them, it can start by itself at every class. Separate apps would need you to enter the timetable three times.

Why no AI?

Every part of the problem has an exact answer. Parsing is pattern matching on day and time forms, scheduling is a search with hard constraints, and planning is gap filling with rules. Rules are predictable and testable, and they run offline. A model could produce a timetable that clashes, or misread a time, and the student would only find out in week one (D-02). The design deals with the hard part of parsing differently: a person reviews the parsed rows before anything uses them.

Why on-device only, with no INTERNET permission?

Privacy, and it keeps working in airplane mode or on a bad campus network. The app reads usage stats and the calendar, and it uses an accessibility service. That is sensitive access, and leaving out INTERNET guarantees that none of it can leave the phone. scripts/test.sh fails the build if the permission ever appears (INV-1).

What are the core invariants?
  • INV-1 on-device only.
  • INV-2 parsed data is used only after review.
  • INV-3 the app changes only its own calendar events and alarms, each tagged with a stable key.
  • INV-4 the phone, SMS, emergency, maps, clock, calendar, Settings and the keyboard are never blocked.
  • INV-5 the scheduler and planner are deterministic.
  • INV-6 a timetable never has a clash and always includes every MUST course; otherwise the result is Infeasible with an explanation.
What is deliberately out of scope?

OCR for scanned PDFs, any ML, accounts or cloud sync, iOS, exam timetables, Play Store policy work, and a voice assistant ("Nova", planned for V2).

Architecture

How is the code organised?

The project is a multi-module Gradle build. core/model, core/parser, core/scheduler and core/planner are pure Kotlin with no Android dependency, so they run as fast JVM tests. data holds Room (schema v10, with auto-migrations). platform holds the Android services: the focus service, the accessibility blocker, the calendar writer, alarms and PDF text. app holds the Compose UI and the ViewModels.

Why keep the core pure Kotlin?

The hardest logic (scheduler, planner, parser) is tested in milliseconds without an emulator, including property tests on thousands of random inputs. It is deterministic because it takes the clock and the data as parameters. Android only appears at the edges.

What is the tech stack?

Kotlin 2.4, Jetpack Compose (Material 3), Room 2.8, AGP 9.4, minSdk 26, targetSdk 35 and compileSdk 37. compileSdk 37 is there because the current AndroidX libraries require it (D-13). PdfBox-Android reads the PDF text. No navigation library and no icon library, which helps keep the APK at 8 MB.

How does the app stay correct when Android kills background work?

Whether to block an app is computed from the clock and the stored state at every window change (D-15b). Alarms and the foreground service only drive the notification, DND and re-arming. A missed alarm or a killed service therefore cannot wrongly block or unblock anything. Alarms are re-armed on boot, on a time or time zone change, and when the exact-alarm permission is granted.

Algorithms

How does the scheduler work?

Each course has options: a single section, or a linked set of lecture, lab and tutorial sections that covers each required kind exactly once. Each option becomes 7 day bitmasks of 5-minute slots (288 bits = 5 Longs), so the clash test is a bitwise AND. The search places the MUST courses first, fewest options first, with backtracking. Then it does a depth-first branch-and-bound over all chosen courses, where each WANT course is either placed or skipped with a reason. It keeps the best K distinct timetables under a ranking key and returns only maximal timetables: a WANT course is skipped only if it really cannot be added.

What is the ranking key?

Compared in order:

  1. The set of WANT courses included, compared by rank, so including WANT #1 beats any combination without it.
  2. A soft penalty, lower is better: +10 per class before the earliest preferred time, +20 per class on a preferred free day, +1 per 10 minutes of gap over the maximum, +5 per class during lunch.
  3. A tie-break by section IDs in course-code order, for determinism.
How do you explain an infeasible timetable?

The scheduler finds a minimal conflicting set by deletion: it drops each MUST course in turn and keeps it out only if the rest still fail. The output is a sentence such as "CS201 and MA101 can't both fit: CS201-A Mon 09:00–10:30 clashes with MA101-A Mon 10:00–11:00". For three or more courses it says "can't all fit together, though any two of them can". Credit limits get their own sentences.

What is the worst case and how did you bound it?

The search is exponential in theory: 10 courses × 5 options is up to 5¹⁰ leaves. The first tie-break could not be bounded, so when nothing clashed and there were no preferences, every leaf tied and the search hit the 3 s cap. Changing the tie-break to section IDs in search order (D-14f) lets the search cut ties exactly, and that case now takes 0.6 ms. A hard cap returns the best result so far, flagged partial.

How does the planner auto-fill work?

The day window runs from wake time plus getting ready to wind-down. It excludes fixed blocks, meals and a 10-minute buffer after each class, and what is left are the free gaps. Tasks are sorted by deadline, then priority, then ID. Each task is placed in chunks of up to the work length in the earliest gap that fits, with breaks between them, until the daily focus maximum is reached. Chunks shrink to fit the 30–45 minute gaps between classes (D-16). Anything that doesn't fit goes to "didn't fit". The planning day rolls over at wake time, not midnight, which matters for late sleepers.

How does the PDF parser work?

PdfBox reads the words and their positions. A university profile maps columns to fields. Day forms (Mon, M/W/F, MWF, TTh …) and time forms (24h, am/pm, ranges) are handled by rules, and continuation lines add meetings or continue titles. Low-confidence fields are highlighted on the review screen. A laptop tool scores the parser against an expected.json golden file. The target is ≥ 95% of fields on a real university PDF, and that measurement is still waiting for a real PDF.

Android platform

How does app blocking work?

An AccessibilityService watches window-state changes. If the app in front is blocked, the service sends the user Home and shows an overlay message. The never-block list is checked first. Shorts and Reels are detected by view IDs kept in a versioned rules file, because those IDs change with app updates.

What went wrong on the real phone that the emulator didn't show?

Three good stories:

  • Never-block was too generous (I-16). "Apps that can dial" on a real phone included Truecaller, Zoom and WhatsApp, and "apps that open maps" included Uber and Zomato, so none of them could be blocked. The fix (D-22) counts only system handlers and the user's default apps for broad intents, and every handler for narrow categories such as Clock and Calendar.
  • DND came on 2 minutes late. Without the exact-alarm permission, Android delays the class-start alarm. The app now asks for exact alarms during setup (D-04).
  • The wake-up alarm screen never opened on a locked Android 15 phone (I-18). Android 15 blocks background activity launches. The alarm is now a broadcast that posts a full-screen-intent notification.
How do you write to the calendar without touching the user's own events?

The app writes to its own local calendar called "Semester". Every event carries a stable key in SYNC_DATA1 (class:<section>:<meeting>), so writing the same event again updates it instead of duplicating it, and deleting goes by key only (INV-3). Each class meeting is one weekly recurring event with EXDATEs for holidays. .ics export is also available.

How are permissions handled?

Each permission is requested only when its feature is first switched on, with a plain reason, and refusing it leaves the rest of the app working (N08). The exception is exact alarms, which the Focus setup card asks for because focus and DND timing depend on them. Without that permission, the wake-up alarm falls back to the system Clock app.

Why is strict mode safe?

Ending a session in strict mode needs a 60-second wait plus a typed sentence. Settings, the dialer and the keyboard are never blocked, so the user can always reach Settings and turn the service off. A blocker that can lock you out of your own phone is a bug.

Testing and quality

How did you test the scheduler?
  • Unit tests named by requirement ID (A07_…).
  • A property test: 600 random requests (fixed seed) compared exactly with an independent brute-force top-K. This check caught a real bug before commit, a credit-minimum bound that ignored unplaced MUST credits.
  • INV-6 tests that no output clashes and every output includes all MUSTs.
  • INV-5 tests that the same input gives the same output, even with the course order shuffled.
What is spec-driven development here?

SPEC.md holds the requirements with IDs and acceptance tests, the data and algorithm contracts, and the roadmap. Behaviour changes only after the spec changes. Insights.md logs decisions (D-xx) and measured findings (I-xx). Status.md is a ≤ 90-line snapshot that each new session reads first. A roadmap step is done only when its acceptance tests pass.

What can't be tested automatically?

A real incoming call during focus, a reboot with a PIN lock, a 3-day battery run (target ≤ 2% per day), a full planned day, and Google Calendar importing the .ics file. These are listed as phone gates, not claimed as done.

Working with Claude Code

What did you do, and what did the AI do?

I set the idea and the constraints: one app, no AI, on-device. I made the product decisions (D-01 to D-04, D-25), ran the phone checks and reviewed the work. Claude Code wrote most of the code and tests and proposed the detailed rules, which are logged as decisions I can override (D-14 to D-24). The spec, the tests and the logs are how I kept control, and the full conversation is in the transcript.

How did you stop the AI from producing wrong code?
  • Every requirement has an acceptance test, and nothing counts as done until it passes.
  • Property tests against brute force for the scheduler and planner.
  • Build checks for INV-1, the SDK levels and the APK size.
  • Real-phone runs, which found three bugs the emulator could not show.
  • User gates: work stops when it needs a real PDF, the phone or a decision.
How did you keep context across six sessions?

Through Status.md, a short snapshot read at the start of every chat that points to the spec and log sections a task needs. The long files are never read whole. CLAUDE.md holds the working rules.

Limits and next steps

What are the weaknesses?
  • The parser has only been scored on a synthetic sample, not on a real university PDF yet (the 95% target is still open).
  • The Shorts and Reels view IDs break when those apps update.
  • Samsung's battery management can still delay background work.
  • The soft-penalty weights are educated guesses.
  • The app is sideloaded, not on the Play Store (accessibility and usage-access policies would need extra work).
What would you build next?

Score the parser on real PDFs and add university profiles, run the 3-day battery test, let users tune the penalty weights, and in V2 add Nova voice control. OCR for scanned PDFs would be the first thing to add if the no-AI rule were relaxed.
